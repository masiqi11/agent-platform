# 沙箱隔离评审（S8）

- 日期：2026-11-17
- 范围：§12.12 SBX-01…10、§14.4、INV-17、ADR-0010（外部执行引擎）
- 方法：逐条对照实现与测试；在本机用真实 docker 29.9 验证网络与防火墙；结论分为「已满足」「部分满足（写明缺口）」「未满足」

## 结论

docker 沙箱在以下条件下可以运行**不完全受信任的仓库代码与外部执行引擎**：

- 使用 docker 沙箱（生产配置强制）；
- 配置 `SANDBOX_NETWORK`，并在宿主机执行 `deploy/sandbox-firewall.sh`。系统状态页没有沙箱警告，才说明防火墙已生效；
- 配置 `SANDBOX_IMAGE_ALLOW`，只允许内部镜像源；
- 有条件时使用 gVisor（`SANDBOX_RUNTIME=runsc`）。

即使满足上述条件，仍有以下剩余风险：

- **共享内核**：不使用 gVisor 时，容器与宿主机共用内核，内核漏洞可能导致逃逸。
- **平台进程持有 docker 守护进程的访问权**：能控制平台进程的人，就能控制宿主机。

因此建议把沙箱放在独立的 runner 主机上（见部署文档）。如果做不到，仍然**只在受信任的内部仓库上运行**（§14.4 的原有声明继续有效）。

## 外部执行引擎的附加评审（ADR-0010）

- **harness 自身的权限设置不可信**：H0 中发现 harness 会用 shell 绕过自身的工具限制。所以平台的边界在服务端：
  - MCP 只列出本角色的工具；
  - 每次调用都经过 `runtime.invokeTool`，并做权限、令牌范围和审计检查；
  - 结论必须绑定提交；
  - git、MR 由平台完成。
- **出网面**：容器只能访问平台的两个端点：
  - `/llm/v1/*`：会做出域检查、预算、脱敏和计量；
  - `/mcp`：要求会话中有正在运行的执行引擎。
- **对抗性 harness**：可能消耗预算（受预算与墙钟限制），可能写入错误代码（必须经过 CI、评审、测试、人工合并审批），可能读取工作区内容（工作区本来就是它的任务范围）。它拿不到其他项目的数据，因为令牌的项目范围只包含 Agent 所属项目。

## 待办（按风险排序）

1. **出口代理与按项目白名单**（SBX-03 剩余部分）：代理在平台进程内或放在独立容器中，按项目放行指定域名，配置变更需要 Maintainer 审批并写审计。
2. **独立的 runner 主机或 rootless docker**：降低「平台进程能控制 docker 守护进程」带来的影响。
3. **docker 下的只读依赖缓存挂载**（SBX-04）。
4. **gVisor 实测**：本机没有 `runsc`，该配置项尚未经过真实验证。
