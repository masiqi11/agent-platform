# ADR-0008：S7 知识库与跨项目问答的实现取舍

- 状态：已采纳（2026-11-17）
- 相关：DEV-SPEC §8.7、§12.9（FR-KB-01…11、KB-补1…7）、FR-CAP-01、INV-04、INV-12、TRAP-3、TRAP-15

## 背景

S7 要让船长基于代码、文档和已确认的决策回答问题，每个结论带可点击的出处；跨项目问题由全局船长路由到各项目船长；无权限的内容不能进入任何候选集。

## 决定与偏差

1. **索引范围（KB-补3）**：只索引默认分支。按 blob sha 增量：内容变化的文件重新分块，删除的文件写墓碑（FR-KB-03），查询一律排除墓碑。仓库绑定时全量建索引；`merge.completed` 和默认分支流水线事件触发增量；每周一次兜底（`kb.weekly`）。
2. **全量重建 = 新版本 + 别名切换（FR-KB-08）**：在旧版本旁边建新的 `project_index` 版本，建完后在同一个事务里停用旧版本、启用新版本，再回收旧片段。查询只读 `is_active` 的版本，所以重建期间不中断，也不会读到建了一半的索引。分块器/分词器版本或嵌入模型变化时自动走全量重建（§8.7）。
3. **分块用启发式，不用语法树**：代码按顶层声明分块（连同前置注释），前导 import 单独一块，超长块按 80 行切窗；文档按标题分块。这是偏差：未引入 tree-sitter，对 TS/JS/Go/Python 等常见写法够用，复杂语法可能切得不准。
4. **排除与脱敏（KB-补1）**：默认排除锁文件、`.env*`、私钥/证书、二进制、构建产物、压缩文件、vendored 依赖、> 1 MB 文件；项目可加排除规则。入库前过密钥扫描，命中处替换为 `[REDACTED]`。只索引已提交的树，所以被 `.gitignore` 忽略的文件本来就不在内。
5. **关键词检索的查询词**：索引沿用 S2 的应用侧分词（中文单字 + 二元组）。查询时只用二元组和英文/标识符词，并去掉「怎么、什么、哪个、如何」等疑问词；只有查询里没有任何二元组时才退回单字。原因：单字 OR 查询几乎命中所有片段，会让「未检索到依据」失效（TRAP-3）。
6. **向量路**：维度固定 768。嵌入模型由租户设置 `embeddingModel` 指定，支持 Ollama `/api/embed` 和 OpenAI 兼容 `/embeddings`，走网关的出域检查、脱敏和计量。CI 与演示用确定性的 `scripted:embed`（字符 n-gram 哈希）。未配置嵌入模型时向量路关闭并在结果里说明。**只靠向量命中的片段不算证据**，回答时不会引用。
7. **SAG2**：先 BM25 取候选，再由模型（`kb.judge`）判断哪些是证据、补充检索词，最多扩展 2 轮；结果按「查询 + 各索引版本」缓存；任何失败退回 BM25（FR-KB-05）。
8. **融合与重排**：三路结果用 RRF（k=60）融合，再按词面重合度微调；问「为什么」时决策加权（KB-补5），群摘要降权 ×0.6。每个结果都列出命中的路、在该路的名次和得分，每路可单独开关（FR-KB-04）。
9. **ACL 前置（INV-12 / FR-KB-07）**：检索开始前先算出调用者有 `project.view` 权限的项目，三路 SQL 都只在这些项目里查。检索结果附每路候选所在的项目，测试据此断言无权限项目从未进入候选集。项目级接口另外要求 `project.view`。
10. **温层（KB-补4）**：只收已确认的决策和每个群的最新摘要；原始群聊不进知识库，只在本群里可搜。
11. **`ask_project_captain`（FR-KB-09）**：只把有词面证据（BM25 或 SAG2 命中）的片段交给模型（`kb.answer`）。模型给出的引用必须能在这些片段里找到，否则剔除（KB-补2 / TRAP-15）；模型失败或剔除后没有引用时，用排名最前的片段生成确定性回答；没有任何证据时回答「未检索到依据」、置信度 low，并给出追问建议（INV-04）。返回答案、引用（项目、仓库、路径、commit、行号）、置信度、`stale`。
12. **过期标记（FR-KB-10）**：索引的 commit 落后于仓库已知的最新提交时，结果和回答标记 `stale`，回答里提示「依据来自旧 commit」，置信度不给 high。引用查看器在该文件之后有改动时提示。
13. **全局船长路由（FR-CAP-01）**：在有权限的项目里按 BM25 命中数选前 3 个，逐个调用其项目船长，汇总时注明来自哪个项目、附引用。所有项目都没有证据时，退回 S4 的「目录 + 摘要」回答方式。
14. **评测集（KB-补6）**：演示项目 30 条问题放在 `apps/server/src/cli/demo-eval.ts`，`bun run seed` 写入 `eval_question`。`bun run kb:eval` 先同步建索引再算 recall@5；后端测试 `s7-kb.test.ts` 也跑同一套题（阈值 0.85），结果写入 `docs/results/s7-eval.json`。
15. **未做**：依赖图（FR-KB-02，P1）；Issue/MR 进冷层；Agent 长期记忆治理（KB-补7）；评测集扩到每项目 100 条（FR-KB-11，P1）；项目目录的 GitLab 同步；真实嵌入模型与真实模型下的 S7 场景。

## 后果

- CI 中用脚本模型 + `scripted:embed` 验证 S7 退出条件：INV-04、INV-12、TRAP-3、墓碑、别名切换、过期标记、跨项目问题「超时相关的计费逻辑在哪个仓库哪个文件」引用 `billing/src/payments-client.ts` 且可打开到对应 commit。
- 评测：后端测试 recall@5 = 0.90（30 题；测试库里混有 TRAP-3 用例插入的临时决策），全新演示库上 `kb:eval` 为 0.933。结果可复现：
  - 早先同一代码的两次运行会得到 0.90 和 0.867。原因是候选片段按 `IN (…)` 取回，顺序不固定，SAG2 判别器看到的候选顺序随运行变化。现已按排名顺序取回；同分时按路径和行号排序；向量查询放宽 `hnsw.ef_search`（避免过滤后近邻被截断）。
  - 重排加了一条通用规则：问题里写出的标识符（如 `placeOrder`）与片段的符号或正文一致时加权。
- 脚本嵌入只反映字面相似度，向量路在真实嵌入模型下的效果尚未测量。
