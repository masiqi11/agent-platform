# ADR-0007：S6 评审、测试、门禁与合并队列的实现取舍

- 状态：已采纳（2026-11-17）
- 相关：DEV-SPEC §12.6、§12.7、§12.8、§12.13、§22.2、INV-08、TRAP-6/7/8/10、ADR-0006

## 背景

S6 要让主场景十步完整闭环：评审 Agent 提意见、开发 Agent 返工、测试 Agent 在独立环境执行并附证据、门禁通过后经人工审批由合并队列合并、关闭 Issue、船长发布完成摘要，全程可审计。

## 决定与偏差

1. **结论绑定提交**：评审与测试记录都写入当时的 head sha。新推送到达（`commit.pushed`）时，旧 sha 上的评审和测试标记为 superseded，合并审批置为 invalidated，合并队列里的该项移出。门禁、状态机守卫和 UI 都只认当前 head 上的结论。
2. **门禁只有一份定义**：`packages/shared` 的 `evaluateGate(facts)` 同时供合并队列和界面使用。门禁项为 CI、评审、（改动范围要求时的）人类评审、测试、无阻塞，以及（`mergePolicy=require_approval` 时的）合并审批。门禁在评审、测试、流水线、审批、推送、状态变更等每个相关事件后自动复查（TRAP-8）。
3. **自动发起合并审批，但不重复追问**：门禁只差审批时，系统自动发起合并审批，并附 NTF-补1 要求的全部证据（MR、改动、评审、测试、CI、成本、风险）。同一提交上的审批一旦有结论（通过、驳回或超时），在出现新提交之前不再自动发起。
4. **INV-08 的落地**：Agent 按角色区分，只有 reviewer 能提交评审，只有 tester 能提交测试，开发 Agent 两者都不能（工具上限 + 权限 + 服务端校验三层）。人按其在该任务上做过的事区分：评审过的人不能再测试，测试过的人不能再评审，接管过任务的人不能评审。
5. **独立检出**：评审与测试 Agent 每轮都从镜像缓存重新克隆，并分离检出到待评审的那个 sha，目录为 `<repo>.review` / `<repo>.test`，用完即删（FR-REL-02）。测试 Agent 先由平台自动跑一遍仓库测试命令并留存日志，再由模型逐条判定验收标准；任何一条 unmet 都不能判定为 passed。
6. **人类评审的覆盖权（TSK-补5）**：人类在 Agent 评审通过、任务已进入「测试中」之后仍可提交「要求修改」。由于状态机没有人类可用的 testing→in_progress 迁移，这种情况不改任务状态，只让门禁失败并把任务移出合并队列，同时写评论。
7. **合并审批驳回不改状态**：与 S3 相同。NTF-补2 要求由驳回人选择转回「开发中」或「阻塞」，但状态机里没有人类可用的 testing→* 迁移。驳回原因写入任务评论，`rejectTo` 存进审批记录。是否在状态机中增加人类迁移留给后续决定。
8. **合并队列（本地仓库）**：在一次性克隆中把任务分支 rebase 到默认分支上。
   - 如果默认分支没有变化，直接用已过 CI 的提交合并。
   - 如果有变化，把变基后的提交推到 `refs/merge-queue/*`，并在该提交上重跑 CI。
   - CI 通过后，带 `AP_MERGE_QUEUE=1` 快进推送默认分支；仓库的 pre-receive 钩子只放行合并队列。
   - 合并之后依次：关闭 Issue → 生成发布记录 → 任务转为 `done`（由 system 以 merge_queue 身份执行）→ 回收工作区 → 在默认分支上跑 CI。
   - 这一串步骤是幂等的：如果默认分支已包含该提交，视为已合并。
9. **队列推进靠事件，不靠轮询重试**：等待 CI 时作业正常结束；`pipeline.completed` 事件，以及每分钟一次的 sweep 兜底，会重新启动处理，并一直处理到队列为空（TRAP-10）。每个等待都有上限：流水线 30 分钟，GitLab「未就绪」2 小时，超时转人工处理。
10. **主干变红就暂停（GIT-补4）**：默认分支的流水线失败时，项目设置写入 `mergeQueue.paused`，并通知 Maintainer。同一分支后续流水线变绿时自动恢复，Maintainer 也可以手动恢复。
11. **冲突不自动处理**：rebase 冲突时列出冲突文件，交给人工处理，并通知 owner 和 Maintainer；后续任务照常合并。由 Agent 处理冲突是 P1。
12. **GitLab 合并路径**：调用 merge API，带上 head sha 作为条件；405/406/422 有限重试，超时后转人工。没有自建 rebase 步骤，交给 GitLab 项目自身的合并设置。2026-11-17 已在本地真实 GitLab CE 17.11 + Runner（docker 执行器）上跑通（`scripts/gitlab-local.sh`，结果 `docs/results/s6-gitlab.json`）。实测发现：GitLab 的合并接口在令牌无权合并到受保护分支时返回 **401** 而不是 403，平台曾因此把仓库误标为「凭据失效」。现已区分：合并返回 401 但令牌仍能读取项目时报「无合并权限」并转人工，仓库保持可用；绑定检查也会在令牌角色不在「允许合并」里时预先告警。平台令牌应为 Developer，受保护分支「允许推送」Maintainers、「允许合并」Developers + Maintainers。
13. **完成摘要只取记录**：船长发布的完成卡片内容来自合并队列项、发布记录、测试运行和验收标准，不调用模型，所以不可能编造证据（TRAP-15）。
14. **回滚（GIT-补6）**：已完成的任务可以一键创建「回滚」热修复任务，内容是 `git revert` 合并提交，并同样经过评审、测试和审批。自动回滚是 P2。

## 后果

- CI 中用脚本模型 + 本地 SCM 跑通主场景十步：后端测试 `s6-main.test.ts`，浏览器测试 `s6-main.spec.ts`。
- 生产前仍需：用真实模型跑主场景（S8）；由 Agent 处理合并冲突（P1）。
