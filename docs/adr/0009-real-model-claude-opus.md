# ADR-0009：用真实强模型（Claude Opus 5.5）跑通主流程，及由此发现的问题

- 状态：已采纳（2026-11-17）
- 相关：LLM-01…13、AGT-补1、CAP、FR-REL、§22.2、ADR-0003（本地小模型）、ADR-0005

## 背景

此前所有场景只用脚本模型（CI）和本地小模型 `gemma4:e2b` 跑过。用户提供了一个 OpenAI 兼容的模型中转站，这次在上面用 `claude-opus-5-5` 跑了 S4（船长）、S6（主场景第 4–8 步）和 S7（知识库问答）三个场景。

- 密钥只放在本机临时文件和平台的加密凭据里，没有进入仓库和日志。
- 中转站的速度大约是每次调用 5–15 秒。

## 结果

| 场景                                                          | 脚本                         | 结果                                             | 调用                                  | 文件                          |
| ------------------------------------------------------------- | ---------------------------- | ------------------------------------------------ | ------------------------------------- | ----------------------------- |
| S4 船长：追问 → 提议 → 建任务分配 → 摘要 → 全局问答 → 无依据  | `test/ollama/s4-scenario.ts` | 6/6 通过，模型自己完成的步骤都没有走兜底         | 5 次，0 失败，0 修复                  | `docs/results/s4-opus55.json` |
| S6 主场景：开发修复 → MR → CI → 评审 → 测试 → 合并队列 → 完成 | `test/ollama/s6-scenario.ts` | 全部通过，用时 5.4 分钟，`main` 上超时改为 3_000 | 35 次，0 失败                         | `docs/results/s6-opus55.json` |
| S7 知识库：3 个项目问题、1 个无依据问题、1 个跨项目问题       | `test/ollama/s7-scenario.ts` | 5/5 通过，引用都指向正确文件                     | 14 次，1 次连接被中转站重置后重试成功 | `docs/results/s7-opus55.json` |

这些脚本都接受 `LLM_BASE_URL` / `LLM_MODEL` / `LLM_API_KEY`，可以对任何 OpenAI 兼容端点重跑。它们不在 CI 中运行。

## 发现并修复的问题

脚本模型和小模型都没有暴露这些问题：小模型能力弱，走不到这些分支；脚本模型的输出又过于规整。

1. **流式解析把 SSE 注释当数据**：中转站会发 `: ping` 保活行，平台把它当 JSON 解析，导致所有流式的船长回合都失败。现在只读 `data:` 行。
2. **并行工具调用的流式分片标错了序号**：中转站把两个并行调用的参数分片都标成同一个 index 并交错发送，客户端无法还原。现在按调用 id 归并分片；如果参数仍然无法解析，同一请求改为非流式重发一次（非流式结果是正确的）。
3. **船长一回合只调用一次模型**：强模型会先查知识库再决定，结果检索完这一回合就结束了，提议改由规则兜底生成。现在只读工具（检索、问项目船长）的结果会在同一回合内回给模型，最多调用 3 次。
4. **摘要格式只写清了一个分区**：提示词只给 `decisions` 写了 `{text, seqs}` 对象格式，模型在其他分区写了字符串，导致整份摘要退回规则生成。现在提示词写明全部分区都用对象，字符串条目按无引用丢弃，不再拖垮整份摘要。
5. **全局问答的材料没有分区标签**：任务标题「排查并修复…」和已确认的决定混在一起，模型把它当成了「已经修复」。现在材料按分区标注，任务一栏注明「进行中或待办」。
6. **Agent 循环用文本回放历史**：之前的步骤以 `<tool_calls>…` 文本放在对话里，强模型开始模仿这种格式，用文本写工具调用（还写错了），任务就此停在开发中。现在改为原生工具消息：OpenAI 兼容端点用 `tool_calls` 和 `role:tool`，Ollama 用 `tool_calls` 和 `tool_name`。脚本模型和不支持工具的模型仍用文本格式。
7. **评审耗尽步数却没有结论**：评审 Agent 把 10 步都用在读代码上，任务一直卡在评审中。现在最后一步只提供结论工具并要求立即给出结论；如果这次结论被校验拒绝，再给一次只能提交结论的修正机会。步数耗尽时停止原因记为 `max_steps`。
8. **评审结论的结构过于宽松**：`criteria` 原来只是任意对象，模型返回的字段嵌套错位，`verdict` 丢失。现在 `criteria` 明确为「验收标准 id → met/unmet/na」，`summary` 必填，无法识别的值直接忽略。

每个问题都补了确定性回归测试，并确认测试在修复前失败、修复后通过。测试用到新增的脚本模型 `search_first`（先检索再提议）和 `explorer`（一直读代码，被迫结论时第一次参数还写错）。

## 后果与未做

- 本轮 Opus 第一轮评审就直接通过，没有触发「评审意见 → 返工」的循环；这个循环只在脚本模型下验证过。
- 跨项目问答里，支付项目船长对「计费」的理解偏宽，引用了自己仓库里的超时代码，计费项目给出的答案是正确的。
- 中转站偶尔会断开连接（ECONNRESET），网关的重试机制吸收了这类错误。
- 成本：中转站没有返回价格，所以没有统计成本。tokens 计数来自中转站的 usage 字段，其中工具调用部分的计数可能偏低。
